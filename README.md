# Лабораторна робота 2: профілювання та оптимізація множення матриць

У роботі досліджено програму множення квадратних матриць типу `float` розміром N×N, написану мовою C++, для якої побудовано FlameGraph, зібрано статистику виконання за допомогою `time -v` та `perf`, виміряно енергоспоживання системи та самого процесора, а також порівняно параметри виконання до і після оптимізації як ключами компілятора, так і зміною вихідного коду.

Реалізовано три варіанти множення:

| Режим | Опис |
|---|---|
| `naive` | три вкладені цикли i-j-k, при цьому матриця B читається по стовпцях |
| `ikj` | перестановка циклів на порядок i-k-j, що забезпечує послідовний доступ до пам'яті |
| `blocked` | блочне множення з розміром блока 64×64 |

## Середовище

- ноутбук Lenovo ThinkBook 14 G6 ABP, процесор AMD Ryzen 5 7530U (архітектура Zen 3, підтримка AVX2 та FMA), 32 ГБ оперативної пам'яті
- Windows 11 з WSL2 (Ubuntu), компілятор g++ 15.2.0, perf 7.0
- для вимірювання енергії використано HWiNFO64, ноутбук працював від батареї

## Структура репозиторію

```
matmul.cpp      вихідний код програми
run_all.sh      скрипт збірки та запуску вимірювань (time -v, perf stat, perf record, FlameGraph)
results/        FlameGraph (.svg), результати perf, асемблерний код (.s)
power/          журнали HWiNFO (.csv)
```

## Збірка та запуск

```
g++ -O0 -g -fno-omit-frame-pointer matmul.cpp -o matmul_O0
g++ -O3 -mavx2 -mfma -g -fno-omit-frame-pointer matmul.cpp -o matmul_O3
./matmul_O3 1024 ikj
```

Для роботи `perf record` необхідно попередньо виконати `sudo sysctl -w kernel.perf_event_paranoid=-1`.

## Результати виконання для матриці 1024×1024

| Варіант | Час | Інструкцій | IPC | Промахів кешу L1 |
|---|---|---|---|---|
| naive -O0 | ~4,1 с | 30,4 млрд | 2,0 | 1,10 млрд |
| naive -O3 | ~4,6 с | 4,6 млрд | 0,3 | 1,14 млрд |
| ikj -O0 | 4,8 с | 38,8 млрд | 3,3 | 72 млн |
| **ikj -O3** | **0,135 с** | **0,83 млрд** | 2,6 | 74 млн |
| blocked -O0 | 5,6 с | 43,6 млрд | 3,2 | 139 млн |
| blocked -O3 | 0,89 с | 9,9 млрд | 4,7 | 153 млн |

Ключ `-O3` сам по собі не прискорив варіант `naive`, оскільки продуктивність обмежена не обчисленнями, а доступом до пам'яті: матриця B читається по стовпцях, тож кожне наступне звернення потрапляє в іншу сторінку кешу, і процесор більшу частину часу очікує на дані, про що свідчить падіння IPC до 0,3 за практично незмінної кількості промахів кешу L1 (1,10 та 1,14 млрд), до того ж компілятор не має права векторизувати накопичення суми `s += ...` без ключа `-ffast-math`, бо порядок додавання дробових чисел впливає на результат.

Прискорення приблизно в 30 разів досягається лише поєднанням двох змін, а саме порядку циклів `ikj`, який робить доступ до пам'яті послідовним і зменшує кількість промахів кешу в п'ятнадцять разів, та ключів `-O3 -mavx2 -mfma`, які дозволяють компілятору векторизувати цей цикл.

Блочний варіант виявився повільнішим за `ikj`, оскільки для матриці 1024×1024 дані й без блокування добре обслуговуються кешем, тоді як додаткові перевірки меж у внутрішніх циклах збільшують кількість розгалужень приблизно в шістнадцять разів і ускладнюють векторизацію.

## FlameGraph

Графіки збережено у файлах `results/flame_O0.svg` (naive, -O0) та `results/flame_O3.svg` (ikj, -O3, матриця 2048×2048); на обох майже вся ширина припадає на функцію множення (99,5 % та 97,3 % відповідно), що свідчить про єдине «гаряче місце» програми. Після оптимізації стають помітними дрібні блоки, зокрема page faults при першому зверненні до виділеної пам'яті (1,8 %), звільнення пам'яті та таймерні переривання Hyper-V, які належать середовищу WSL, а не самій програмі; раніше вони були непомітні, бо множення займало майже весь час виконання.

## Асемблерний код

Код збережено у файлах `results/matmul_O0.s` та `results/matmul_O3.s`. При `-O0` внутрішній цикл функції `mul_ikj` складається з 36 інструкцій на один елемент, усі змінні зберігаються в стеку (`[rbp-...]`), а обчислення виконуються скалярними інструкціями `movss`, `mulss` та `addss`; при `-O3 -mavx2 -mfma` той самий цикл містить шість інструкцій на вісім елементів одночасно (`vmovups ymm`, `vfmadd213ps ymm`, `vmovups`), де регістр `ymm` має ширину 256 біт і вміщає вісім чисел `float`, а інструкція `vfmadd213ps` виконує множення та додавання за одну операцію. У варіанті `naive` з `-O3` компілятор використав лише скалярні `vfmadd231ss`, що пояснює відсутність прискорення.

## Енергоспоживання

Програму запускали циклом тривалістю 60 секунд із записом показників у HWiNFO, причому потужність усієї системи визначали за датчиком розряду батареї, а потужність процесора за датчиком «Повна споживана потужність ЦП»; для розрахунків використано стабільні значення за останні приблизно 20 секунд запису, а енергію одного запуску обчислено як добуток потужності на час запуску (60 с, поділені на кількість запусків).

| | Простій | naive -O0 | ikj -O3 |
|---|---|---|---|
| Процесор, Вт | 2,59 | 8,3 | 11,45 |
| Уся система, Вт | 5,28 | 11,5 | 14,8 |
| Запусків за 60 с | | 13 | 582 |
| Час одного запуску, с | | 4,62 | 0,103 |

| Енергія одного запуску | naive -O0 | ikj -O3 | У скільки разів менше |
|---|---|---|---|
| Процесор понад простій, Дж | 26,3 | 0,91 | 29 |
| Система понад простій, Дж | 28,6 | 0,98 | 29 |
| Процесор повна, Дж | 38,3 | 1,18 | 32 |
| Система повна, Дж | 53,1 | 1,53 | 35 |

Час виконання скоротився в 45 разів, тоді як енергоспоживання лише в 29-35 разів, оскільки потужність зросла (потужність процесора з 8,3 до 11,45 Вт): векторні AVX2-інструкції задіюють більше функціональних блоків за такт, а процесор перестає простоювати в очікуванні пам'яті, тому економія енергії досягається не зниженням потужності, а значно коротшим часом виконання.

Серед обмежень методу слід зазначити, що датчик батареї усереднює вимірювання й відстає від реальної потужності, тому значення для всієї системи наближені, а також що вимірювання проводились у WSL2, де лічильники RAPL недоступні, через що й було використано HWiNFO.

## Примітка щодо термінів здачі

Роботу здано невчасно, оскільки вона виявилась для мене надзвичайно складною: довелося працювати на Windows і з нуля налаштовувати Linux-середовище (WSL), а потім освоювати `perf`, FlameGraph та вимірювання енергоспоживання; додатково виконання роботи наприкінці суттєво ускладнювалось постійними відключеннями електропостачання, які не дозволяли стабільно працювати за комп'ютером і проводити вимірювання.
